01

Document contract

This is the canonical explanation of why orc is shaped this way. Code and tests remain the executable truth for exact behavior.

Normative

What this document owns

  • System boundaries and sources of truth.
  • Replay, durability, permission, and lifecycle promises.
  • Deliberate tradeoffs and the reasons they were accepted.
  • Conditions that should cause a decision to be revisited.
Descriptive

What remains in code

  • Wire-protocol fields and harness-version compatibility.
  • Policy constants, CLI flag details, and visual styling.
  • Point-in-time audit findings and remediation status.
  • Test counts, model catalogs, pricing, and dependency versions.
Core thesis

The deterministic program decides what work exists; the supervisor decides when and whether that work may run; harnesses and executors perform the real work. The journal is the durable handshake between those worlds.

When this document and the implementation disagree, treat that as design drift to resolve. Do not silently promote an accidental implementation detail into a product promise, and do not preserve prose that the code cannot honestly support.

02

Goals, non-goals, and principles

Orc chooses a small durable core and delegates everything else to native tools.

P-01

Promises are the graph

Ordinary async control flow expresses fan-out, joins, data dependencies, and failure handling. No parallel DAG API is maintained beside the language.

P-02

Record facts, then replay

Orc records call identity and completion order. Resume re-executes the pinned program and delivers those durable facts rather than checkpointing a VM heap.

P-03

One run is one directory

Files, native locks, and content-addressed results carry all run state. A run is inspectable and portable at the user-account boundary.

P-04

Native controls first

Claude, Codex, and the operating system enforce what they already know how to enforce. Orc does not build a second shell, sandbox, or policy language.

P-05

Fail closed, explain clearly

Changed history, unknown authority, unsupported capability, or ambiguous resume fails loudly. Where certainty is impossible, the product lowers its promise.

P-06

YAGNI is architectural

No distributed coordinator, remote agent, auth system, plugin scan, or recovery wizard exists until a demonstrated workflow requires one.

Goals

  • Deterministic orchestration around nondeterministic AI work.
  • Concurrent promise-native leaf execution with bounded resources.
  • Crash-safe resume without repeating durably completed leaves.
  • Explicit write authority, approval bubbling, and live observability.
  • Shared registry-backed command semantics across CLI and MCP, with a thin SDK and direct monitor projection.

Non-goals

  • A distributed workflow service or multi-user control plane.
  • Exactly-once external side effects.
  • A universal side-effect sandbox for agent integrations.
  • Replay compatibility across arbitrary orc upgrades.
  • Automatic discovery of ambient plugins or extensions.

04

Programming model

An orc program is a deterministic coordinator, not a privileged automation script. 

import type { Program } from "@karowanorg/orc-sdk/program";

const program: Program = async ({ agent, parallel, phase }) => {
  const inventory = await agent("List the modules.", {
    schema: {
      type: "object",
      properties: {
        modules: { type: "array", items: { type: "string" } }
      },
      required: ["modules"]
    }
  }) as { modules: string[] };

  const audits = await parallel(
    inventory.modules.map((name) => ({
      id: `audit-${name}`,
      prompt: `Audit ${name}`
    }))
  );

  return phase("synthesis", () =>
    agent(`Synthesize: ${JSON.stringify(audits)}`));
};

export default program;

Program-visible primitives

  • agent(prompt, options) creates one journaled leaf.
  • parallel(specs) starts independent lanes and returns settled outcomes.
  • settle(promise) converts one rejection into data the program may handle.
  • phase(name, fn) lexically labels calls, including across awaits.
  • ext.name(payload) invokes a trusted, explicitly registered host extension.
  • log(message) records orchestration narrative outside deterministic state.
Identity

Call order assigns sequence

A leaf receives the next sequence number when the VM dispatches it. Its canonical specification digest becomes replay identity.

Isolation

Agent context starts fresh

Each invocation gets its own prompt/session context and the shared brief. Program-level results move as explicit JSON; leaves may still observe shared filesystem or external state.

Constraint

JSON is the value boundary

No functions, accessors, sparse arrays, cycles, non-finite numbers, or class instances cross the VM, journal, harness, or result boundary.

Product effect

Authors gain ordinary TypeScript async composition and lose ambient runtime power: no clock, randomness, filesystem, network, or runtime module loading inside the program. Real-world work belongs in leaves.

05

Determinism and replay

Orc does not serialize a VM. It recreates the VM and replays durable completions.

  1. 01 · CALLVM emits a canonical leaf spec and sequence.
  2. 02 · CHECKSupervisor applies caps, write gate, extension schema, and identity.
  3. 03 · WALCall and attempt records are appended before dispatch.
  4. 04 · RUNHarness executes through the chosen executor.
  5. 05 · VALIDATEResult becomes strict canonical JSON and is schema checked.
  6. 06 · COMMITResult body is stored; completion is fsynced.
  7. 07 · DELIVERExactly one promise settles, then QuickJS drains to quiescence.

Replay invariants

  • The exact frozen bundle must match its manifest hash.
  • Every replayed call must match sequence and specification digest.
  • A completion must target a promise the replayed program actually requested.
  • Every historical call suffix must be re-created or remain legitimately pending.
  • Completion delivery order is journal order, not sequence order.
  • Each delivery is followed by a complete deterministic microtask drain.

Loud divergence

Resume refuses to guess when it sees:

  • a changed program bundle;
  • a changed leaf specification;
  • a dangling completion;
  • an unconsumed historical call suffix;
  • committed JSONL corruption; or
  • an ambiguous terminal failure frontier.
Run-once boundary

A leaf with a durable effective done record is not dispatched again. This is logical run-once execution, not physical exactly-once side effects: work interrupted before durable completion may still exist externally and may be retried or re-oriented.

06

Persistence and sources of truth

Every run is inspectable under $ORC_HOME/runs/<run-id>, defaulting to ~/.orc/runs/<run-id>.

Run artifacts, authority, and durability
ArtifactPurposeAuthorityDurability / integrity
manifest.jsonPinned launch configuration, program digest, permission and policy inputs.AuthoritativeImmutable after creation by design.
program.bundle.jsExact code executed live and during replay.AuthoritativeSHA-256 checked against manifest before supervision.
journal.jsonlCalls, attempts, cumulative attempt costs, completions, retry markers, terminal finish.AuthoritativeAppend-only; fsync per append; only an unterminated tail is recoverable.
results/<sha>.jsonCanonical leaf and final result bodies.AuthoritativeContent-addressed; body digest checked on read.
traces.jsonlAttempt revisions, timings, tools, model, session, logs, token detail.ObservationalAppend-only sidecar; journal facts drive deterministic state, while legacy cost and abandoned-approval recovery still consult traces.
control.jsonlCancel requests and approval decisions from external surfaces.Input channelAppend-only and fsynced; finish records scope consumed controls to an ownership epoch.
report.htmlStatic projection of current state.DerivedAtomically replaced; safe to regenerate or delete.

Why the journal is body-free

Completion records reference result digests instead of embedding large bodies. This keeps replay metadata small, makes identical values naturally deduplicate, and allows body integrity to be checked independently.

Why traces are not truth

Traces are useful and lossy: they can contain multiple revisions. Current durable completions and costs in the journal override sidecar detail whenever the two disagree. The supervisor still consults traces for legacy cost and abandoned-approval recovery, so “observational” describes the authority boundary rather than zero runtime use.

07

Supervisor lifecycle

One supervisor owns one run from replay preflight until all write-capable work has stopped.

  1. OWNAcquire native advisory lock; detect holder loss.
  2. OPENOpen appenders and control watcher.
  3. REPLAYVerify program and deliver effective history.
  4. RE-ARMPersist retry only after clean replay.
  5. EXECUTEDispatch up to maxParallel and process controls.
  6. FINISHAppend terminal record and abort remaining work.
  7. DRAINWait for writers, bound readers, close files, release lock.
Concurrency

Bounded dispatch

The supervisor uses one run-wide maxParallel pool. There is no implicit write serialization or per-host quota; completion timing varies and the journal freezes the order observed.

Retry

Read and write differ

Retryable read-only failures receive a bounded number of fresh attempts. Write leaves never auto-retry during a live run.

Shutdown

Safety before availability

Ownership remains held until write tasks settle. Abort-resistant read-only tasks receive a short bounded grace so they cannot wedge the run forever.

Fail-forward resume

  1. Rebuild the effective completion set by applying append-only retry markers.
  2. Replay the pinned program and verify all historical call identities.
  3. Automatically retry only an unambiguous terminal causal failure.
  4. Preserve failures the program already caught and observed as data.
  5. For an unfinished or retried write leaf, prepend current working-tree state and instruct the agent to inspect before acting.
  6. Never rewind durable history and never blindly repeat a write.

Budget enforcement

Each attempt start and its latest cumulative reported cost are journaled. The supervisor sums all attempts, including retries, marks the run failed, and aborts in-flight leaves when observed spend passes budgetUsd.

Control epochs

Finish records store how far the owner consumed control.jsonl. A new owner starts from that durable offset, expires abandoned approvals, and does not replay stale authorization into resumed work.

Budget semantics

The budget is a reactive stop-on-observed-spend cap, not a prepaid reservation. Usage reports arrive after work has consumed tokens, and concurrent leaves may report together, so the final amount can exceed the configured threshold.

08

Harnesses, executors, and extensions

Vendor protocols and transport details terminate at narrow interfaces.

Harness contract

One leaf in, normalized events out

A harness discovers capabilities and invokes a LeafRequest. It emits normalized model/session, tool, usage, denial, result, and error events. Core shape-checks events and validates the delivered result, but trusts adapter cardinality and the size of observational payloads.

Executor contract

One argv

Executors spawn commands, collect output, and expose basic file operations on the local machine.

Built-in adapter execution paths and behavior
AdapterExecution pathImportant behavior
Claude Anthropic Agent SDK controlling the system Claude CLI. Native structured output, sessions, and canUseTool approval bridging.
Codex codex app-server JSON-RPC spawned through the executor. Model discovery uses native model/list; strict output schemas are normalized and restored.
Local executor Detached process group with TERM then KILL escalation. Group signaling includes descendants; stdout/stderr drain is bounded after leader exit.
Trusted extension seam

Explicit configuration only

orc.config.* may register in-process harnesses, NDJSON executables, cost rates, and defineLeaf extensions. There is no ambient scan. Extension registration—not the program—owns its readOnly metadata.

Trust boundary

Custom code can lie

Core validates event shapes and declared result schemas, but it cannot prove a custom harness or extension honored authority metadata, emitted one terminal event, or bounded every trace payload. Configured adapters are trusted operator code.

Permission model

Write authority, approval behavior, and filesystem confinement are separate dimensions.

Permission controls and guarantees
ControlScopeGuaranteeNot a guarantee
allowWritesRun manifestA write-declared leaf cannot dispatch unless the run granted writes.It does not itself confine where an allowed write leaf can write.
readOnlyLeaf specificationBuilt-in command and file-mutation tools cannot be restored by approval or bypass mode.Configured hooks and MCPs, including Computer Use, are not disabled; their side effects are outside the promise.
approvalModeRun manifest, mapped by harnessControls whether native requests bridge to an operator, deny automatically, or run autonomously.Approval is not filesystem confinement and cannot weaken readOnly.
sandboxRun manifest, write leaves onlyBuilt-in write paths use native confinement to cwd + sandboxDirs and fail if the harness cannot enforce its boundary.It is not a universal boundary around configured external integrations.
Precedence

readOnly wins over every approval mode. For a write leaf, sandbox:true wins over bypass for filesystem roots. The run-level allowWrites gate must be open before either path executes.

Approval-mode mapping by harness
Approval modeProduct meaningClaudeCodex
manualAsk the operator for tool authority.SDK canUseTool callback.App-server approval requests bridge to controls.
accept-editsPermit native in-scope file edits; ask for other authority.Native accept-edits.Auto-accept confined file changes; bridge commands and out-of-scope edits.
autoNo interactive prompt; denied native requests are reported.dontAsk.approvalPolicy: never.

Configured integration tradeoff

Read-only leaves keep configured MCP eligibility in both built-in harnesses because tools such as Computer Use are core product value. That narrows the promise to built-in command/file mutation. Sandboxed Claude write leaves go further and isolate inherited settings/MCP to protect declared roots; Codex relies on its native workspace sandbox and does not expose an equivalent global MCP switch. Exact integration availability is therefore not a cross-harness sandbox guarantee.

10

Registry operations, SDK, and monitor

CLI and MCP exhaustively interpret one operation registry. The SDK wraps selected operations; the monitor projects run files directly.

Zod-first operationsName · documentation · mutation hint · input schema · handler
CLI · exhaustiveCommands, help, arrays, negated flags, and JSON catalog generated at runtime
MCP · exhaustiveSame handlers and schemas as stdio tools with readOnlyHint annotations
SDK · selected facadeZod input types plus ergonomic Orc and OrcRun wrappers for common workflows

What “surface equivalence” means

Where a surface is registry-backed, it shares the input schema and handler. It does not mean identical coverage, output transport, or interaction style across CLI, MCP, SDK, and UI.

The monitor is deliberately direct

The UI reads journals and traces and appends controls without interpreting ALL_OPS. This keeps a local projection simple, but control validation must not be assumed equivalent to CLI, MCP, or SDK.

Two meanings of read-only

OpDef.readOnly is a coarse MCP/command mutation hint, not a security boundary or purity claim: report writes a derived file and open may start a local server or browser. Leaf readOnly is the harness permission contract described above. They must not be conflated.

Detached launch

A package-owned child entry builds the same registry, acquires ownership, and returns success only after an IPC ready signal or a concrete startup error.

Status projection

Journal facts establish calls, attempts, completions, retries, and finish. Latest trace revisions overlay timing, harness, and running detail.

Bounded waiting

The registry wait operation returns timeout and retry-handoff detail. The SDK’s ergonomic OrcRun.wait() returns only the latest status.

Monitor design

Static report

Each run gets a self-contained report.html. It is a projection, written with temporary-file plus rename, and may auto-refresh while the run is active.

Live monitor

A framework-free Node HTTP server binds loopback, renders the same projection, and sends lightweight SSE ticks. The browser refetches HTML fragments; the server does not maintain a second state store.

Projection rule

The UI may be stale or absent without changing run correctness. A journal record can change deterministic state; a trace or report can only explain it.

11

Decision ledger

These choices are intentional. Each includes the cost and a concrete reason to reconsider it.

D-01

Express orchestration as promise structure

WhyAsync TypeScript already expresses dependencies, joins, branches, and failure handling.
CostThe complete future graph is not statically visible; validation can preview only the first frontier.
Revisit whenUsers need graph-wide scheduling or visualization before any leaf runs.
D-02

Replay a frozen bundle instead of checkpointing VM state

WhyCall identity plus durable completions is smaller, inspectable, and independent of QuickJS heap serialization.
CostThe program must remain deterministic and cannot use ambient time, randomness, or I/O.
Revisit whenRequired programs cannot be expressed as deterministic orchestration around leaves.
D-03

Persist each run as plain per-run files

WhySingle-user local operation needs persistence and inspection, not infrastructure.
CostNo distributed ownership, transactional query engine, or multi-host control plane.
Revisit whenRuns must be shared, scheduled remotely, queried at scale, or coordinated across machines.
D-04

Freeze observed completion order

WhyConcurrent AI work is nondeterministic; replaying the order actually observed reproduces promise continuations.
CostDelivery is serialized one completion per VM drain even when several leaves finish together.
Revisit whenA new deterministic batch-delivery rule proves materially faster and can be versioned safely.
D-05

Store result bodies by digest

WhyKeeps the WAL body-free, verifies integrity, and naturally deduplicates identical JSON.
CostOne logical completion spans a body file and journal record; full power-loss atomicity needs more filesystem work.
Revisit whenResult sizes or remote artifact storage justify a dedicated blob layer.
D-06

Fail forward; never rewind

WhyExternal side effects cannot generally be rolled back. Durable observations must stay observed.
CostAmbiguous failures require a new run; write retries must inspect partial state and remain idempotent.
Revisit whenA domain supplies explicit compensation semantics or idempotency keys end to end.
D-07

Compose native permission controls

WhyClaude and Codex understand their tools and sandboxes better than a generic imitation.
CostThe shared promise is intentionally narrower than each harness’s full behavior; some sandbox integration availability differs.
Revisit whenNative protocols expose a small common control that closes a demonstrated user-facing gap.
D-09

Share one registry where command semantics match

WhyCLI and MCP commands, machine catalog, defaults, schemas, and handlers should not drift independently.
CostThe SDK is intentionally partial and the UI is a direct projection; equivalence applies only to registry-backed paths.
Revisit whenA registry-backed surface needs semantics the shared handler cannot faithfully represent.
D-10

Require explicit extension registration

WhyAuthority and replay dependencies should not change because an ambient package happened to be installed.
CostOne config entry is required for custom harnesses and leaf kinds.
Revisit whenA signed, inspectable plugin catalog solves a demonstrated onboarding problem.
D-11

Keep the monitor local, derived, and framework-free

WhyThe filesystem already holds state; HTML fragments and SSE are enough for a live single-user monitor.
CostNo remote sharing, multi-user auth, push service, or rich client state model.
Revisit whenThe monitor binds beyond loopback or becomes a shared operational surface.
D-12

Do not support replay across arbitrary orc upgrades

WhyVersioned VM semantics and migrations would be a large system before v0.1 needs them.
CostThe recorded version is not enforced and config/policy are not pinned; an old run can fail or continue under current adapter behavior.
Revisit whenLong-lived production runs must span deploys and a compatibility window is defined.

Known limits and deferred work

These are honest ceilings, not an automatic backlog. Revisit only when the trigger becomes real.

Boundary
Configured integration side effectsreadOnly and sandbox cover built-in command/file paths, not all hooks or MCPs.
User effectComputer Use remains valuable and available when configured, but “read-only” is not globally side-effect-free.
Revisit triggerA high-assurance mode is required and both harness protocols expose a simple enforceable integration switch.
Accepted
Budget overshootSpend is enforced after cumulative usage updates, without pre-reserving concurrent leaves.
User effectA configured cap limits continued work but is not an exact billing ceiling.
Revisit triggerExact financial enforcement or provider-side reservation becomes available and necessary.
Deferred
Power-loss durabilityJournal/control appends and result temp files are fsynced, but all files and directory entries are not.
User effectProcess-crash recovery is the promise; sudden machine/storage loss may lose the newest rename or run creation.

YAGNI

User effectLocal simplicity wins; a hostile local browser context remains a conditional control risk.
Revisit triggerRemote binding, sharing, multi-user use, discoverable IDs, or a demonstrated browser exploit.

User effectAn unfamiliar permanent error may consume extra attempts, while a newly worded transient error can be misclassified.
Revisit triggerHarnesses expose stable structured error classes that can replace the text heuristic.
Boundary
Trusted local run filesDigests protect pinned code and result bodies, but manifests, journals, controls, and traces are not an authenticated adversarial log.
User effectAccidental corruption is often detected; a local actor with filesystem access remains inside the trust boundary.
Revisit triggerRuns are imported, shared, or audited across mutually untrusted users or machines.
Accepted

User effectThe simple design is easy to inspect but very long or highly chatty runs will eventually refresh more slowly.
Revisit triggerMeasured run sizes make refresh latency noticeable; add indexing only then.
Accepted

User effectUnsupported platforms fail closed; network-filesystem/distributed lock semantics are not promised.
Revisit triggerWindows or shared-state deployments become supported targets.
Accepted
Write-task livenessThe owner waits indefinitely for a local write task that ignores cancellation, preserving exclusivity over responsiveness.
User effectCancel/resume may wait; force-kill remains an operator action. Read-only tasks receive bounded grace.
Revisit triggerA visible stopping state or kill escalation is needed for real uncooperative harnesses.
Accepted
Detached resume handoffPreflight releases ownership before the child acquires it; the child lock and readiness signal remain authoritative.
User effectA concurrent resume may win the race and the other caller receives a startup error.
Revisit triggerConcurrent resume becomes common enough to justify an ownership-transfer protocol.
Boundary
Trusted adaptersCustom harnesses, extensions, config, and native agent integrations run with user authority.
User effectResult/schema shapes are checked at delivery, but a malicious adapter can ignore permissions, emit multiple terminal events, or flood trace detail.
Revisit triggerUntrusted third-party adapters become a supported distribution model.
Accepted
Inline result ceilingProgram, leaf, prompt, and error caps protect memory and journal behavior; no automatic artifact spill exists.
User effectLarge inline answers fail clearly and must be summarized or written as separate artifacts.
Revisit triggerReal workflows repeatedly need large structured results.
